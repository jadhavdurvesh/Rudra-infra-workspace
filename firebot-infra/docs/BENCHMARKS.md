## How to read this honestly
- AKSHARA: the first row is what your robot code pays per `emit()`; the second includes the writer thread and disk.
- DHARA vs SQLite: the comparison writes DHARA with `sync="none"` and SQLite with a commit per put (WAL, synchronous=NORMAL),
  so it is NOT a like-for-like durability comparison. Measured separately on the same sandbox: DHARA does ~227,000 puts/s with `sync="none"`, ~286,000 with `sync="interval"` (fsync about once a second) and ~4,700 with `sync="always"` (fsync every write; this depends heavily on the storage device). Use SQLite unless a benchmark of
  your own workload, at your required durability, shows you need DHARA.
- SETU+KAVACH: signing every message costs roughly a 5x drop in request rate here (Ed25519 in Python). Sign selectively if a
  message class does not need it, or move hot paths to a transport with its own authentication (mutual TLS).
- LIPI: the "none" row only measures memory copying. Pick a codec from the ratio/speed trade-off on YOUR data.
- SPANDA: a simulated comparison (virtual time), not a network measurement. Benchmark against TCP/QUIC before adopting it.
- ANANTA: the SQLite store answers the whole dashboard in milliseconds at this size; use ClickHouse for volume.
